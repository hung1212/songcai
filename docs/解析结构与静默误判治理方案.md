# 解析结构与静默误判治理方案

2026-10-06追加：按用户最新要求，v0.4.6取消解析升级人工确认，直接采用新规则；历史记录和旧赔付留存，真实业务歧义继续提示。下面涉及升级确认的设计已由本条替代。

日期：2026-10-06。状态：已实施于v0.4.5，使用和验证见[解析升级与Codex核验使用说明](解析升级与Codex核验使用说明.md)。以下诊断记录描述修复前v0.4.4的行为，方案章节保留作为实现依据。

建议沿用“本地规则＋必要时AI核验”，先修正消息结构识别，再增加原文与结果的一致性检查。这次不是用户写法不规范，而是程序把业务文字识别成了玩家名。单独增加一个冒号替换规则，无法覆盖类似错误。

## 1. 本次输入的确定含义

```text
新澳奥  四肖中特 ：龙牛狗蛇 200
```

| 字段 | 正确解释 |
| --- | --- |
| 市场 | 新；此处“新澳奥”是市场表达 |
| 玩法 | 四肖中特 |
| 选号 | 龙、牛、狗、蛇，4个不同生肖 |
| 计费 | 整项200元，一项，合计200元 |
| 中奖条件 | 特码生肖属于上述4个生肖之一 |
| 玩家 | 沿用当前玩家；没有署名则归本单玩家 |

在这个字段位置，有无冒号、使用中文或英文冒号、字段间增加空格，不应改变业务含义。四肖中特不能转换为4个独立特肖，更不能展开号码后每号200元。

## 2. 已确认的错误链路

修复前 v0.4.4 的处理顺序是：先用冒号猜玩家名，再解析投注。

1. `senderHeader()` 把“新澳奥  四肖中特”识别成玩家名；它对玩法的排除规则遗漏了“肖中特”。
2. 后续只收到“龙牛狗蛇 200”，明确玩法已丢失。
3. 裸生肖按现有默认口径展开成特码号码。2026马年这4个生肖共16个号码，因此算成16×200＝3200元。
4. 结果没有解析警告，默认的疑难AI队列也没有收录这一行。

影响不限于金额：

- `旧 四肖中特：龙牛狗蛇200` 会丢失“旧”市场，并因假玩家切换重置为“新”。
- 假玩家和市场可能继续影响后续省略写法。
- 自动账目标题复用了同一个玩家识别函数，可能生成“新澳奥  四肖中特”这样的错误标题。软件按同标题覆盖，升级时必须处理标题变化；本次没有读取用户数据库，也没有证据表明用户账目已被覆盖。
- `新 四肖中特` 独占一行、下一行写 `龙牛狗蛇200` 时，当前玩法续行规则也会丢失“四肖中特”。这是另一处结构问题，不能只修冒号。

主要代码位置：[玩家识别与解析](../desktop-client/src/core/parser.js)、[自动标题](../desktop-client/src/core/ledger.js)、[AI核验输入](../desktop-client/src/core/ai-review.js)、[AI请求组装](../desktop-client/electron/ai-review-service.cjs)。

### 2.2 当前AI为什么可能漏掉

当前疑难队列主要检查解析报错、含数字的未识别文字和玩法继承。这条错误结果没有触发这些条件。

即使选择整单核验，实际请求也只发送已经去掉前缀的 `body` 和推导后的上下文。本例AI看到的是“龙牛狗蛇 200”，看不到“四肖中特”；旧市场的同类输入还会携带错误的“新”上下文。因此，增加调用次数不能替代修正输入证据。

## 3. 第一层：统一识别结构，保留原文

### 3.1 共享业务词典和结构规则

玩家识别、投注解析、原文高亮、自动标题和AI校验共用一套版本化定义，涵盖市场别名、玩法、分类、数量要求、计费单位和继承策略。例如“四肖中特”作为完整玩法识别，不能先拆成“四肖”或“特”。

统一输出结构：

```text
原文与消息边界
→ 玩家／市场／玩法／选号／计费词／金额／备注及其原文位置
→ 明确声明、合法继承或默认的判定依据
→ 标准投注对象
→ 本地计算与原文一致性检查
```

原文保持不变。全半角、已确认别名等规范化只用于识别，并保留规范化位置到原文位置的对应关系；高亮和核验均可定位到原词。

### 3.2 冒号应结合两侧内容判断

| 结构 | 判定 |
| --- | --- |
| 四肖中特：龙牛狗蛇200 | 玩法＋选号金额 |
| 旧 四肖中特：龙牛狗蛇200 | 市场＋玩法＋选号金额 |
| 新 红波：100 | 市场＋分类玩法＋金额 |
| 小明：旧四肖中特龙牛狗蛇200 | 玩家＋投注正文 |
| 旧：1 2各100 | 市场声明＋投注正文 |

冒号前可以被完整解释为市场、玩法或分类组合时，优先作为业务声明，并结合后文验证。不能用“包含某个业务字”判断整个名字，例如姓名里的“新”不应自动变成市场。

来自收件箱、微信导入的明确发送人信息，或者用户绑定的玩家，优先作为身份依据。纯文本中的名字与玩法确实同名、且存在两种合理解释时，才提示归属争议；无署名仍按本单玩家，不增加警告。

不能全局删除冒号、空格、小数点或换行来修复。它们也承担玩家边界、号码分隔、小数金额和分组作用。

### 3.3 单独处理声明续行和上下文

- 独占一行的“旧 四肖中特”是尚未完成的声明；同一消息内后续合法的“龙牛狗蛇200”应承接它。
- 一条已完成投注之后是否继承玩法，按对应玩法的明确规则处理；不把所有玩法一律延续到下一条。
- 市场与玩法分别维护。沿用用户已确认的口径：同一玩家的后续省略市场继续继承；明确重设市场时更新；切换玩家时默认新。两边为新、旧，三边为新、旧、港。
- 消息边界必须保留。待补全的一笔不能跨另一条独立消息或另一位玩家随意拼接；消息边界与市场是否继续继承是两个独立问题。

例如：

```text
小明：旧1各10
四肖中特：龙牛狗蛇200
特肖虎100
```

三笔均属于小明、旧市场，金额分别为10、200、100元，共310元；第二行不能制造一个名为“四肖中特”的新玩家。

## 4. 第二层：成功结果也要检查

新增一轮直接对照保留原文的检查，不能仅检查被清理后的正文，否则前面的信息丢失仍然不可见。

| 检查 | 要求 |
| --- | --- |
| 关键证据完整性 | 原文的市场、玩法、计费词、选号和金额必须有解释，不能被误归为玩家或备注后消失 |
| 明确玩法一致性 | 原文明确写“四肖中特”，结果必须匹配；不能静默回退默认特码 |
| 数量与选号 | 四肖中特要求4个不同生肖；缺失、重复导致数量不符时待确认，不能补生肖 |
| 计费依据 | 整项、每号、每肖、每组分别校验；红波100与红波各100必须保留区别 |
| 市场与归属 | 显式市场不得被默认市场覆盖；玩家切换必须有可靠依据 |
| 金额计算 | 金额以分计算；按该玩法的注数和市场分别计算，核对已声明合计 |
| 原文覆盖 | 未解释且可能改变投注含义的文字进入疑难项；客套话和无关备注不增加提示 |

默认特码只适用于已支持的裸号码、裸生肖等表达，并且没有相冲突或遗漏的业务证据。单价、总额异常可作为复核线索，但不能只因金额大就认定错误。

对唯一可确定的写法直接正确解析；只有确实存在不同业务解释时才待确认。待确认部分不能当成已确定金额或用于完成结算，其他确定投注仍可正常展示。

建议在明细中展示简短解释，点击可定位原文：

```text
新 ｜ 四肖中特 ｜ 龙 牛 狗 蛇 ｜ 整项200元 ｜ 合计200元
```

## 5. 第三层：让AI核验完整业务证据

保留现有“疑难核验／整单核验”的入口，调整输入和校验方式：

1. 新增结构疑点触发条件：疑似业务前缀被当成姓名、显式词与结果矛盾、关键文字未解释、声明续行丢失等。即使本地返回成功，也进入核验。
2. 发送完整相关业务片段、必要的原始前文声明、消息边界以及本地暂定结构。已确认姓名用匿名标识代替；仍可能是业务文字的前缀不能先删掉。请求仍服从软件的AI开关与用户配置。
3. 要求AI根据原文提出结构化解释并引用依据，再与本地结果比较，不能只让AI认可已有结果。金额、号码展开、中奖和赔付仍由本地计算。
4. 候选必须覆盖原文明确信息。不能只验证“AI重写后的投注能被解析”，还要验证它与原文市场、玩法、计费和选号一致。
5. 确定规则即可解释的常见格式离线完成；未确认俗称或真正冲突才交给AI和用户处理。模型置信度及“双方一致”均不等于绝对正确。

缓存、已确认表达和异步响应需绑定原文、消息上下文、业务日期、解析器版本和核验版本。升级后，基于旧错误边界产生的解释不得直接复用，必须重新校验；过期响应不能覆盖用户新编辑的内容。

## 6. 用格式变体测试覆盖一类问题

已有测试未覆盖本次“玩法＋冒号被当姓名”的组合。后续把用户确认的案例作为固定验收集，并为同一业务含义生成合法的格式变体。

| 测试维度 | 示例和要求 |
| --- | --- |
| 字段分隔 | 中文／英文冒号、有无空格、全角空格；仅在不改变语义的字段位置变换 |
| 玩法数量词 | 四肖中特、4肖中特；完整玩法识别结果一致 |
| 数字形式 | 200、２００、二百、贰佰；已支持且含义明确时金额一致 |
| 合法续行 | 玩法声明与选号金额分行；保留真实消息边界 |
| 市场 | 新、旧、港、两边、三边；分别验证每市场金额 |
| 玩家 | 本单玩家、显式玩家、同玩家延续、切换玩家、名字含业务字 |
| 农历日期 | 生肖展开号码在农历新年切换，不能随测试当天日期漂移 |
| 同行多笔 | `新4.5.16.17.28.41各20米29.40各10米` 应保留两段单价，共140元 |
| 必须有差别 | 红波100是整项100；红波各100是逐号1700；不能因标准化而相等 |
| 必须待确认 | 四肖中特只有3个不同生肖、特肖三中三1 2 100、缺金额、取消或修改指令 |

每个样例独立标注预期的玩家、市场、玩法、计费单位、选号和分组、注数、单价、总额。涉及结算的样例再使用固定开奖和赔率验证中奖与赔付。不能只断言“没报错”或“总额相同”，也不能用同一个解析器生成自己的标准答案。

仅对语法允许的格式变换要求等价。例如移动字段间冒号可以等价；改变小数点、号码边界、每号／整项标记或消息边界则不保证等价。不能把任意空格和标点删除当作测试生成规则。

## 7. 旧账复核和升级处理

解析规则改变可能同时改变总额、号码分布、特码集合和中奖结果，升级应提供差异复核：

1. 在保留原始文本、业务日期、玩家上下文的基础上，按旧版和新版分别解析，生成差异报告，不直接批量覆写旧账。
2. 显示玩家、市场、玩法、计费、金额和赔付的变化以及原文依据；如果没有对应开奖与赔率，只展示投注差异，不补造赔付。
3. 升级过程中固定已有账目ID和保存标题，避免重新推导自动标题后触发意外的同名覆盖。用户之后主动新建、改名、保存的同名覆盖规则继续沿用。
4. 已保存的结算快照保留。受影响结算标为待复核，经确认后的解释生成新计算版本，不能静默改写旧赔付。
5. 差异项按原因和相同上下文归组，方便批量核对；存在未解决争议时不能完成结算。

本次只检查了合成样例，没有对用户现存账目做重算或迁移。

## 8. 推荐实施顺序与交付标准

| 阶段 | 实施范围 | 验收标准 |
| --- | --- | --- |
| 第一阶段：修复已复现问题 | 共用业务前缀识别；修正玩家和标题判断；明确玩法不可丢失；声明续行；补齐本次回归案例 | 本次16条样例按预期通过；原文有无冒号均整项200；小明／旧市场的连续3笔仍共310；真正姓名识别不回退 |
| 第二阶段：检查与核验 | 原文位置和字段依据；独立一致性检查；AI完整业务输入；上下文和缓存版本；明细解释 | 无法把明确玩法静默算成另一玩法；本地和AI都能看到完整证据；真正冲突待确认，普通文字不提示 |
| 第三阶段：扩展和升级 | 全玩法格式变体测试；历史账目差异预览；已有结算与标题保护；金额和赔付联动验收 | 固定样例逐字段符合预期；升级不意外合并账目、不覆盖已保存结算；受影响账目可逐项追溯 |

第一阶段优先解决已确定的计算错误；后续阶段把同类格式变化纳入自动验收，减少反复补例外规则。历史复核与标题保护须随正式升级一并安排，不能在直接重算用户旧账后再补。

本文补充[标准解析规则与AI核验方案](标准解析规则与AI核验方案.md)，不改变已确认的玩法、生肖农历切换和市场继承口径。

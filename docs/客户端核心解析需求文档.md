**已确认：`六肖中特虎牛兔马蛇龙100` 等“多肖中特”首版归为特肖，多个生肖合为一笔，整项金额100；特码所属生肖命中其中任意一个即满足其业务中奖含义。不能按每肖100或六连肖处理。支持一肖、二肖中特、三肖中特等数量写法。**

### 1.1 “正确解析”的定义

- 信息完整、规则确定的输入：玩家归属、玩法、市场、选项、分组、计费单位、单价、总额均正确。
- 非投注内容：明确归类为发送人、期号、标题、金额校验信息、单位续行、聊天内容等，不参与计费。
- 信息缺失、语义冲突或有多种合理解释的输入：保留原文，标出具体位置和原因，由用户补充或选择解释。
- 不允许把“未识别”默认为特码，不允许静默丢弃非法号码，也不允许用猜出的金额补齐总额。
- 全部原文片段均能追溯到解析结果或明确的非投注/异常分类；有未解决项目时，汇总应显示“已确认金额，仍有待处理项”。

样例中确实存在残缺输入，因此“覆盖所有样例”包括正确识别有效内容和正确提示异常，不能等同于把每行都算成有效投注。

## 2. 调研范围与现状

### 2.1 样例基线

`number-of-statistical-plug/oglang-test` 共包含 **52 个 `.og` 文件、4,720 个物理行、3,786 个非空行**。行数使用 UTF-8 读取后 `splitlines()` 统计。非空行包含发送人、单位、汇总及聊天消息，不代表投注笔数。

另有 `text.html` 和系统文件，不列入首版投注文本验收；项目根目录的 `test-parse.og` 可作为补充用例。样例缺少统一年份和人工确认的预期结果，因此目前不能给出可信的自动解析正确率。

样例呈现的主要特征：

| 特征 | 实际输入或出处 | 对解析的要求 |
| --- | --- | --- |
| 原始聊天文本 | `老友:`、`李沐航（副号）:`、`[OK]`、`[特殊消息]` | 识别发送人和消息边界；同一发送人连续消息继承市场，切换发送人重置；名字中的“新/老”等字不能改变市场 |
| 多种分隔符 | `01.13`、`01/13`、`01十13`、`01一13`、`01@13` | 根据语境识别，不全局替换所有汉字或符号 |
| 中文及混合金额 | `各两`、`各一百五十`、`各2O`、`2OO元` | 金额词法与号码词法分开处理 |
| 同行多笔 | `新澳平特猴100，马龙各50`，见 `李军.og:27` | 生成 3 个生肖选项、两种单价，合计 200 |
| 跨行共享金额 | `旧澳.og:21–22`；`新的一天/新的一天1.og:36–37` | 按完整语句拼接，不能机械逐行取最后一个数字 |
| 明确的组合分组 | `李沐航/李沐航旧澳.og:32–35` | 保留原来的 10 组三号码，不能把所有号码混成一个复式池 |
| 单独/后置市场 | `李沐航/李沐航3.og:2–4`；`香港.og:59–61` | 识别消息末尾市场声明及其作用范围 |
| 多市场 | `两边 1 2 3 10`、`新老特兔猪各十`、`香新…` | 按市场分别记录，市场内与总体金额可核对 |
| 自带合计、数量 | `共25码`、`=170`、`合计500`、`共56组每组50` | 提取声明值用于校验，不能把它们当号码或另一笔金额 |
| 重复及叠加 | `31.36.34.34…各十`、`鼠 + 12 100` | 区分重复下注、选号集合去重及展开后的重叠 |
| 残缺/歧义 | `老五不中 1000`、`特串5`、`…18.4046各20` | 缺号码、引用不明、号码粘连要分别提示 |
| 文件名不代表市场 | `新澳.og` 有香港输入；`李沐航旧澳.og` 有新澳输入 | 正文明确声明优先，不能只按文件名分类 |

| `src/utils/index.ts` | 全局继承上一个市场、过滤部分杂文、插入换行 | 上下文限于当前文档中同一发送人的连续内容，切换发送人重置；分词与切句不修改用户原文 |

源码审阅发现以下风险，首版不能照搬：

1. `parser()` 对无效输入直接跳过，用户无法判断漏了哪些内容。
2. 金额经常取最后一个数字，不能可靠处理同行不同单价、共享金额、数量声明和期号。
3. 连码入口主要采用全组合逻辑；`three.ts` 另有不同分组逻辑，两者不能视为统一规则。
4. `/平/` 和 `数字+肖` 等宽松匹配可能混淆平特、连肖和“六肖中特”。
5. `0头`、`0尾` 展开会产生 0；普通号码统计还可能出现“被过滤的号码仍进入总额计数”的不一致。
6. `waveNumber` 的 `红大`、`红小`、`绿大`、`双的`、`小的` 等集合存在明显不一致，应重新生成并核验。
7. 生肖表在模块加载时依据当前时间选定，不能确保历史文件重算稳定。
8. 全局 `lastThemeType` 可能受不同文件/解析调用影响；“香”“澳”等别名也未完整覆盖。
9. “死”“活”“子”“家”“金”等全局字符替换可能误改名字、普通句子或已经完整的词。
10. 多玩法和多市场处理存在明细、号码汇总与总额口径不一致的风险，须以统一数据结构重新汇总。

上述属于静态源码发现，本次未运行完整插件，也未生成旧插件的全量输出基线。

## 3. 规则理解与适用边界

### 3.1 官方基础与本地业务的区别

香港赛马会公开资料确认：号码范围为 1–49；每期摇出 7 个不同号码，前 6 个称为“攪出号码”，第 7 个称为“特别号码”。官方单式选择 6 个号码，复式从更多号码中组合，胆拖要求固定号码进入每一注。

本项目样例的特码、特肖、连肖、平特、特串、不中，以及新澳/老澳等名称，是本地业务的文本及计费口径。官方页面用于核对基础概念，**不能据此认定这些玩法、市场及赔率是官方产品**。首版完成文本解析和玩家分市场投注记账；赔付统计是已提出的后续目标，首版预留关联数据，暂不实现开奖接入、中奖判断、赔率或派彩计算。

### 3.2 首版玩法字典

下表“业务含义”用于区别文本，不构成已确认的结算规则。

| 玩法 | 业务含义及拟定计费方式 | 必须区别的情况 |
| --- | --- | --- |
| 特码号码 | 以特别号码为目标；每个所选号码一份，金额 = 计费号码份数 × 每号金额 | `12各50` 与 `12、50各10` 的金额位置不同 |
| 生肖展开特码 | `鼠各号10` 等先按规则表展开生肖号码，再逐号计费 | 与 `特肖鼠10` 逐肖计费不同；本年生肖通常有 5 个号码，其余 4 个 |
| 特肖/独肖/一肖 | 以特别号码所属生肖为目标；明确逐肖下注时，每个生肖一份 | `一肖` 需避开 `平特一肖`；`特肖…各号` 属单位冲突，见 Q06 |
| 连肖 | 选择 k 个生肖构成一组；如二、三、四、五连肖，通常关注开奖范围内各生肖是否出现 | 单式一组；复式 `C(n,k)` 组；“平特三连肖”仍需保存连肖分组语义 |
| 连码 | 二中二、三中三、三中二等号码组合；金额按完整所选组合计 | 三中二每组选择 3 个号码，不能按 `C(n,2)` 计注；中奖条件暂不实现 |
| 特串 | 本地常见为两号码串联；旧项目按两号码组合计费 | 单个生肖特串、沿用上一笔号码、`4个特串10` 需另行确认 |
| 平特肖 | 按所选生肖计费，通常表达在含特别号码的开奖范围内出现相应生肖 | 不把生肖展开后再次乘号码数量 |
| 平特尾 | 按尾数选项计费 | `平特1尾1000` 为 1 个尾选项，不是 5 个号码各1000 |
| 平特号码 / 平码 | 都需要单独保留玩法名称，按号码选项计费 | “平码”是否仅指正码、是否与“平特号码”等价，待确认 |
| x不中 | 选择 x 个号码为一组，旧项目支持 1–10；复式为 `C(n,x)` | 缺号码/不足 x 个不能按特码兜底；中奖范围待未来结算阶段确认 |
| 多肖中特（首版归特肖） | **已确认**多个生肖为同一项，特码所属生肖命中任意一个；按整项金额计费 | `六肖中特…100`总额100，不是600，也不是六连肖；覆盖一肖、二肖中特、三肖中特等 |

连肖/连码的简写拟支持 `二连/两连/3连/三肖/3有/三友`，但必须结合对象为号码还是生肖判断。“连码”和“连肖”保留独立玩法，不因当前总额相同而合并。

**多肖中特的识别优先级**：先识别完整的“几肖中特”，再处理泛化的“几肖/几连”。对`新澳六肖中特虎牛兔马蛇龙100`输出：特肖、新澳、六个生肖选项、命中任意一个、整项计费、1份、单价100、金额100。内部保留原始名称和“任一命中”的语义，供未来结算扩展；首版只解析统计。声明数量须与不同生肖数量一致，例如“六肖中特”只列5个生肖应提示缺项。不能因该规则把没有“中特”的普通“二肖/三肖”全部改成合肖。

### 3.3 单式、复式、分组与胆拖

- **单式**：恰好 k 个不同选项组成一组。
- **复式**：一个选项池有 n 个不同选项，选 k 个，组数为 `C(n,k)`。
- **明确列组**：`三中三 11-25-36。21-38-47。06-22-39。08-17-19 各组25` 是 4 组，共 100，不是从 12 个号码取 3 个的 220 组。
- **连肖顿号分组（2026-10-10已确认）**：`二连肖牛羊、羊猪、羊兔、牛兔各30`是4组共120元，逐组计算中奖，不合并为复式。详见[连肖顿号分组说明](连肖顿号分组说明.md)。
- **胆拖**：固定 d 个胆，从 m 个拖码选 `k-d` 个，理论组数为 `C(m,k-d)`；每组须包含全部胆，胆拖不得重叠。含生肖的“兔拖龙”是否表达两组号码交叉配对，见 Q05。
- **单号拖生肖二中二（2026-10-10已确认）**：`二中二30拖鼠各10` 为固定30分别与鼠肖号码组成二中二，马年4组共40元。按农历年展开，显式保留每组；只按正码配对结算。详见[二中二拖生肖规则](二中二拖生肖规则.md)。
- **单肖拖多个生肖二连肖（2026-10-10已确认）**：`二连肖马拖（兔羊猪虎鸡）各20`为马兔、马羊、马猪、马虎、马鸡5组，共100元，按各组是否含当年生肖使用二连肖赔率。详见[二连肖拖肖规则](二连肖拖肖规则.md)。
- **单号拖生肖特串（2026-10-11已确认）**：`特串45 拖 鸡各10`固定原文号码45，马年搭配鸡的10、22、34、46，4组共40元，每组按一个正码加特码结算；原文写44则固定44。详见[特串拖生肖规则](特串拖生肖规则.md)。
- **多玩法共用选项**：`死活` 拟展开为三中三和三中二各一份；`复三。复四。复五。各组20` 分别计算后相加，不混为一个玩法。
- **同义词不重复计费**：`死 三中三` 表示同一个玩法；`三中三死活` 若确认“死活”为两玩法，也只产生三中三、三中二各一份。
- **省略复式**：样例有 `新三中三17.25.35.23.20.46各10`，旧代码会按复式。拟兼容“单个无明确分组的号码池按复式”，仍须与显式分组区分，见 Q04。

### 3.4 生肖、头尾、波色与分类集合

**生肖切年规则（用户已确认）**：以农历正月初一为切换日，不能在公历1月1日切换，也不能按固定“延后1–2个月”估算。农历2026年为马年，农历2027年为羊年；例如公历2027年元旦之后、当年春节之前，仍使用上一农历年的马年表。

建议按以下行为落地：

1. 新建内容时，以业务日期计算所属农历年，自动选择生肖表；默认业务日期为当天。
2. 使用经验证的农历日期转换或逐年春节边界表，不能只硬编码2025/2026。首版至少验证2025、2026、2027及随后一年的交界。
3. 根据当年生肖排列生成01–49的映射：当年生肖对应01、13、25、37、49，其他生肖依序对应剩余号码；结果须与固定测试表核对。羊年的羊应对应这5个号码。
4. 文档保存业务日期、所用农历年、`ruleSetId`及版本。历史文件重开时使用已保存日期，不随电脑跨年静默改算；改业务日期时明确展示重算结果。

## 4. 文本解析需求

### 4.1 输入与原文保留

**FR-01** 支持粘贴、编辑、打开 UTF-8 `.og` / `.txt`；支持中文路径、LF/CRLF、UTF-8 BOM、全角数字及常见不间断空格。解码失败应提示，不产生乱码结果。

**FR-02** 保存原文和位置信息，标准化文本作为内部副本；不得沿用自动给原文件插入换行的做法。每个结果保留文件、消息、起止行列及原文片段，可点击定位。

**FR-03** 支持批量导入整个样例目录进行核对；每个文件的默认市场、发送人上下文、规则集互相独立。按文件展示异常与统计，并在选定的记账范围内跨文件按玩家和市场汇总。玩家身份可复用，但不同文件之间不继承市场；全目录总额按文件金额相加，不自动去除相同文件内容。

### 4.2 规范化、金额和符号

**FR-04** 在明确的词法位置支持以下写法，并记录用到的转换：

| 类型 | 需要支持的写法 | 限制 |
| --- | --- | --- |
| 数字 | `01`、`１`、`O8`、`2O`、`2OO` | O/o→0 仅限数字片段；`l9` 拟作 19 的候选修正，须可见 |
| 中文金额 | 一至九、十、百、千、万、两/俩；`一百五十`、`一千五百` | `一千三` 拟兼容 1300；财务大写不是首轮必要输入，可后续扩展 |
| 金额引导 | 各、各号、各数、每号、每个号、每个号码、每组、各组、各注、买、下、落、号、个、`=`、`@`、`/` | 同一符号也可分隔号码，必须结合完整语句判断 |
| 金额单位 | 元、米、块、斤、个、钱 | 首版拟按 1:1 数值计费，保留原单位；不表示自动换汇 |
| 生肖别名 | 免→兔、兔子→兔、猎→猪、鸣→鸡；子→鼠 | `子鼠` 拟识别为一个鼠；`羊子` 中“子”含义不明，不能无条件增加鼠 |
| 玩法别名 | 死→三中三、活→三中二、复式/复试/复实、两连/二连、三友/3有 | 不对整段普通文本直接做字符替换 |
| 市场别名 | 新澳/新澳门/新奥/新门；老澳/旧澳/澳门旧；香港/港/香；新老/两边/三边 | 已确认默认新、两边=新+旧、三边=新+旧+港；新凹已确认为新市场；单独澳/奥/门/粤、新噢门、臭门等需分别确认，不做无限模糊匹配 |

`各.5` 在现有样例中很可能是分隔符后金额 5，但也可能被理解为 0.5；首版不得在无既定规则时自行选择。若支持小数，建议只接受明确的 `各0.5`，内部使用整数分或十进制定点数；金额最小单位见 Q07。

`17一29`、`7十19` 中“一/十”可作连接符，但 `各十` 必须解析为金额 10。`//50` 在样例中是金额写法，不能一律当程序注释；`*`、`+`、`-` 也不能直接解释为数学运算或区间。

### 4.3 切句与上下文

**FR-05** 一条逻辑投注可以跨物理行，一行可以生成多条投注。按照消息边界、玩法、金额结束位置和显式分组识别语句，不按标点单一切分。

**FR-06** 金额前置、后置和共享金额均须有专门规则。例如：

- `特肖包40钱牛`：待业务确认后可识别为牛特肖、金额 40，不因生肖在末尾而漏掉。
- `平特肖兔50龙50`：两个生肖分别 50。
- `01 03 …` 换行接 `13 21 … 各40`：第一行无独立金额时，可共享末尾金额；若第一行末数字也能解释为金额，须保留歧义。
- `三中三` 后连续多组括号，最后 `各2`：共享玩法和单价，保留各组边界。
- `特串5`、`加四连10`、`4个特串10`：存在对之前选项的引用，需明确引用对象；不能任意取上一行的全部数字。

**FR-07** 市场与玩法分别维护上下文。**默认市场已确认为“新”**，新建文档或导入没有市场配置的文件时自动使用该默认值，无需用户先设置。文件名不得自动改变默认市场。

| 市场写法 | 解析后的市场集合 | 确认状态 |
| --- | --- | --- |
| 无市场声明、无可用的明确上下文 | 新 | 用户已确认默认值 |
| 两边 | 新、旧 | 用户已确认 |
| 三边 | 新、旧、港 | 用户已确认 |
| 新老 / 新旧 | 新、旧 | 项目兼容写法；老与旧归为同一市场 |

**市场继承规则（用户已确认）**：优先级为“当前语句明确市场 > 当前发送人连续内容中最近一次声明的市场集合 > 默认新市场”。具体按以下顺序处理：

1. 先识别发送人，后解析投注正文。第一次出现发送人，或发送人与上一段不同，先将市场集合置为`[新]`。
2. 当前正文明确声明新、旧、港、两边或三边时，用该声明**替换**当前市场集合，不与旧集合累加。
3. 后续没有声明市场时，继续使用该发送人的当前市场集合。换行、空行、玩法变化或重复出现相同发送人标题均不重置。
4. 出现另一发送人时开始新的连续段，重置默认新市场；该人有明确市场则立即覆盖默认值。按这条切换规则，A→B→A时，A返回后也从新市场开始，不恢复A上一次连续段的旧市场。玩家账目仍归入同一个A。
5. 两边/三边作为完整集合继承。例如同一人先写两边，再写没有市场的特肖，后者也计入新、旧；再次明确“港”后，后续只继承港。
6. 已完成的投注记录保存最终市场集合及其来源：当条明确、继承自哪一条声明，或默认。修改上游发送人/市场后，重新解析受影响的后续范围，不能只改当前行。

用户给出的验收场景：

```text
小明：旧 1 2 3 各100元
特肖虎 100元
张三：特肖虎100元
```

| 玩家 | 新市场投注 | 旧市场投注 | 港市场投注 | 投注合计 |
| --- | --- | --- | --- | --- |
| 小明 | 0 | 400 | 0 | 400 |
| 张三 | 100 | 0 | 0 | 100 |
| 合计 | 100 | 400 | 0 | 500 |

小明第二条继承旧市场；张三切换为新发送人且没有声明市场，因此使用新市场。市场只决定归属，不影响各自投注单价。

消息尾部单独的`香港` / `新澳`存在于旧样例中。草案建议只回填该发送人**当前消息内**没有当条明确市场的投注，再用于后续继承；不能回填其他玩家或该人更早的消息。它与“声明只向后生效”的边界仍见Q03，不能将后置回填规则误称为用户已经确认。

`平特一肖` 后出现明确号码、`每号`或`特码`等，应重新判断玩法，不能无限继承前一个玩法；只有语法可确定为续写时才继承。发送人字段中的“新/老/港”不是市场声明，普通聊天内容、单位续行和合计行也不自行声明市场；识别到不同发送人的消息头则按上述规则切换身份。

### 4.4 金额计数、重复与汇总校验

**FR-08** 每笔记录必须有明确的 `amountBasis`：每号、每肖、每尾、每组或整项。金额计算遵循：

2026-10-12补充：行首市场名称前的三位数字可作为期号备注忽略。“285新澳三中三：01、10、18、21、28、31、41、49每组3”按56组各3元计168元，原文及期号备注保留。详见[行首期号备注识别说明](行首期号备注识别说明.md)。

2026-10-11补充：`3，4头双数各十五／3，4头单数各五`在30–49中筛选单双，每笔10个号码，150元＋50元＝200元，按逐号特码统计和赔付。详见[头数单双筛选说明](头数单双筛选说明.md)。

2026-10-11补充：`包猪数+绿波数各十`为两笔每号10元的特码，马年40元＋160元＝200元，重叠号码32、44各累计20元。“数／号码／数字”表示逐号，“包猪40”仍按40元总额均分。详见[包生肖数与加号逐号投注](包生肖数与加号逐号投注.md)。

```text
每市场金额 = 计费份数 × 单价
多市场总金额 = 各市场金额之和
复式组数 = C(不同选项数量, 每组选项数)
明确列组金额 = 各完整组金额之和
```

同一玩法和号码重复出现在不同投注语句中，按独立下注累计；不自动删除重复消息。单笔特码中的重复号码及生肖展开重叠，旧代码倾向累计，样例也存在符合累计的合计，草案建议保留计费份数并提示重复。组合选号池中的重复不能当作不同号码，应提示去重后如何影响组数，见 Q08。

多肖中特使用`amountBasis=整项`：六个生肖是这一项的覆盖范围，**不是6个计费份数**。`二肖中特虎牛100`为1份共100；明确写`特肖虎牛各100`则是每肖计费，共200。若整项关键词与“各肖”等单位冲突，提示确认，不擅自选择金额较大或较小的解释。

多市场记录应显式生成各市场金额。选择“全部”时相加，选择“新澳”时只展示新澳；任何界面筛选都不能更改解析结果或计费规则。

**FR-09** `共25码`、`共10组`、`合计500`、`=170` 等作为数量/金额声明保存并核对，不用于强行修正计算值。金额合计可能属于上一笔、一个段落或整个消息，要保留作用范围；不明确时提示“校验范围待确认”。

例如 `在这里.og:3–32` 实际列出 28 条三中三、每条末尾 100，但又写“共56组每组50”：两种描述金额都为 2800，组数和单价却冲突。必须提示，不能仅因为金额相同就判定全部正确。

**FR-10** 号码需为 01–49，金额必须有限且符合允许精度和正值规则；明确号码区出现 0、50、120、4046 等，不能静默丢掉或自动拆分。金额超过 49 是合法的，不得误用号码校验。缺玩法必需参数、组合大小不足、重复组内号码均应具体报错。

**FR-11** 大复式先精确计算组数，再按需展示组合；不能为了算总额一次性生成所有组合。超过资源阈值仍可展示精确组数和金额，并提示组合明细未全部展开。

### 4.5 玩家识别与分市场记账

**FR-12 玩家归属**：每笔投注同时保存原始发送人名称和玩家ID。支持`小明：旧…`这类同行发送人+正文，以及`小明:`独立一行的标题；标题后的投注沿用当前玩家，直到下一个发送人标题。姓名识别不能依赖冒号单一符号，避免把`特码：`、`新澳：`、`平特肖：`误当玩家。

没有发送人的独立输入允许用户指定账目所属玩家；未指定时按本单玩家统计，不警告、不阻止赔付。不同账目的默认玩家ID独立，不能归入前一个账目；正文明确姓名优先。

首版按清理首尾空白后的明确名称匹配玩家，保留原始名称及来源。不自动把昵称、副号或近似名字合并，例如“李沐航”与“李沐航（副号）”；如需合并，提供明确的玩家映射并保留原名称。发送人切换按原文中的发送人身份判断，账目映射不应让不同发送人意外共享市场上下文。

**FR-13 算账维度**：核心汇总为“玩家 × 市场”的投注金额表，列出新、旧、港及玩家合计，支持查看玩家在某市场下的玩法小计和原始投注明细。同时提供各市场总计和全部玩家总计；跨文件汇总时按照已确定的玩家ID归集。

记账范围必须可见。首版建议使用业务日期/记账批次区分账目；能识别期号时另存市场及期号，无法识别时允许暂存为未指定期号的批次，不能猜期号。跨日期/批次的合并必须由用户明确选择，避免将历史文件和本期金额无提示混算。

**FR-14 可重复核算**：解析、筛选或修改同一份原文，是更新该来源当前有效的投注记录与汇总，不能每点一次解析就追加一笔账。每笔投注及其各市场明细需有可关联的ID。重复导入相同内容可以提示，但不得无依据删除实际重复下注。修正玩家、市场或金额后，保留原文和变更依据，支持回溯核对。

**FR-15 赔付扩展（后续阶段）**：后续需要按同一“玩家 × 市场”维度计算、汇总赔付金额。首版即保存玩家、投注ID、市场明细ID、业务日期/批次、期号（若有）、玩法、计费方式和规则版本，供赔付结果关联。

赔付记录建议与原始投注记录分开：未来保存关联投注及市场、结算批次、采用的赔率/规则版本、赔付金额和结算状态。不直接覆盖投注金额；多市场投注按各自市场分别关联赔付。未接入/未结算时显示“未结算”或“—”，不能用0暗示已算出无需赔付。

后续接入赔付前，再确认各玩法中奖条件、赔率、赔付是否含本金、退回/作废口径及结算修订方式；不在本轮假定净输赢或应收应付公式，也不把统计的投注额当作已收款、赔付额当作已付款。

## 6. 数据与技术方案建议

建议使用 **Electron + TypeScript + Vue 3**：现有解析代码以 TypeScript 为主，可保持一套解析核心，并分别打包 Windows/macOS。此为技术建议，不是用户已指定的选型；若安装体积有明确要求，可再比较 Tauri。

建议结构：

```text
desktop/       文件操作、窗口、安装打包
ui/            文本编辑、玩家分市场账目、明细、异常处理
parser-core/   纯 TypeScript，独立于桌面框架和界面
accounting/    玩家归属、批次和投注汇总，预留后续赔付关联
rule-sets/     市场、生肖、波色、别名、规则版本
fixtures/      经标注的样例、预期结果和异常分类
```

解析流程：**原文留存 → 识别发送人、消息和元信息 → 词法标准化 → 按发送人维护市场上下文 → 玩法及分组分析 → 语义校验 → 号码展开/组合计数 → 定点金额计算 → 玩家分市场记账与声明校验**。

建议的最小结果字段：

| 对象 | 必需字段 |
| --- | --- |
| 文档/批次 | 文档ID、记账批次ID、原文、文件来源、业务日期、业务时区、农历生肖年、默认市场、可选的默认玩家、规则集ID与版本、人工确认记录 |
| 玩家 | 玩家ID、显示名称、原始发送人名称及来源映射；没有署名时使用本账目独立的默认玩家ID |
| 片段 | 原文起止位置、消息ID、发送人标识、发送人连续段ID、原文、标准化文本、分类、归一化说明 |
| 投注 | 投注ID、玩家ID、来源片段、批次/业务日期、玩法、原始玩法名、市场集合及继承来源、原始选项、展开选项、命中语义（如多肖中特为任一生肖）、分组模式、每组大小、份数、单价、计费单位、各市场金额、总额 |
| 投注市场明细 | 明细ID、投注ID、玩家ID、市场、期号（若有）、该市场投注金额、规则版本；作为后续赔付的关联对象 |
| 组合 | 单式/明确列组/复式/胆拖；显式组或可延迟展开的组合描述 |
| 诊断 | 错误码、级别、来源位置、具体原因、可选解释、是否排除金额 |
| 声明校验 | 原文声明数量/金额、关联范围、计算值、差额、通过/冲突/范围不明 |
| 后续赔付记录（预留设计） | 赔付记录ID、关联投注市场明细ID、结算批次/版本、赔率和规则依据、赔付金额、结算状态；首版不生成计算结果 |

拟定状态为：`parsed` 已解析、`needs_review` 待确认、`invalid` 数据无效、`metadata` 元信息、`ignored` 无关内容。允许一条消息部分成功，但未确认部分不计入已确认金额。

解析相同文本、业务日期、玩家映射及相同配置必须产生相同结果；当前发送人和市场集合仅属于当前文档的解析状态，不使用跨文件的全局“上一个市场”，也不从玩家历史账目恢复市场。当前日期只用于新内容的默认业务日期，历史解析不隐式依赖机器当前年份。原文按普通文本展示，不能直接插入 HTML。

### 8.2 全量验收要求

- 对全部52个 `.og` 文件建立固定清单及内容哈希；覆盖空文件、残缺输入和聊天杂文。
- 每个逻辑片段标注：来源位置、发送人/玩家、预期类型、玩法、市场及继承来源、选项、单价、份数、金额、诊断。标注不以旧插件输出或原文“合计”自动代替人工核对。
- **已确认有效样例的字段及金额正确率100%**；歧义/无效样例的诊断符合预期。未确认样例独立统计，不能通过全部标为待确认来满足解析目标。
- 片段覆盖率100%：任何非空输入都被解释、归类或报错，不能静默丢失。
- 同一筛选范围内，明细金额之和 = 玩法汇总之和 = 市场汇总之和 = 玩家汇总（含本单默认玩家）之和 = 总额；每个玩家的各市场金额之和等于该玩家投注合计。特码号码金额之和仅与特码小计比较，不能与含连肖/连码的总额混比。
- 同组内同一发送人重复标题和玩法变化不重置市场；空白行后默认新澳，切换发送人也重置；多市场完整继承，显式市场替换；A→B→A不恢复旧上下文。姓名里的“新/老/港”不视为市场声明。
- 重复解析同一来源不重复记账；修改发送人/市场后重算受影响范围；跨文件只汇总已确定的玩家账目，不共享解析上下文。未知玩家金额单列，不误归他人。
- 固定规则集后，多次解析、跨文件切换、应用重启、系统日期变化及LF/CRLF变换，不改变业务结果。
- 农历切年验收：公历元旦前后但尚未到春节时生肖年不变；农历除夕结束到正月初一时，新业务日期切换新生肖年；验证马年→羊年，并确认历史文档不自动改表。春节日期必须由已验证的历法数据确定。
- 补充有意义的边界用例：0/49/50、0头/0尾、金额缺失/0/负值、小数、单双与波色交集、组合数量不足、重复号码、生肖切年、多市场继承及超大组合。
- 建议性能目标：普通500行文档在暂停输入后500ms内刷新；约5000行样例全量解析2秒内完成。实施时固定测试设备与统计口径，组合明细使用延迟展开，不将这些目标视为已测结果。

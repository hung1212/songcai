# 微信记录录入：GitHub 项目调研与方案对比

调研日期：2026-10-05  
适用项目：松财桌面客户端（macOS / Windows）  
用户环境：Intel Mac；本机已安装微信 **4.1.13（269602）**，版本来自应用的 Info.plist。  
核验范围：阅读 11 个候选项目的公开说明，并抽查关键源码和许可证；没有安装、运行这些项目，也没有读取用户聊天或测试微信自动化。

## 1. 结论

**有可参考的其他方案，建议把“读取指定私聊”和“导入聊天数据包”加入设计，保留用户提出的收藏批量读取。**

针对记录量大、主要为一对一私聊的情况，最值得先验证的是：在松财绑定玩家和微信聊天后，选择要处理的范围，由软件读取聊天、处理图片并生成待确认账目。若这条路线可靠，可以省掉每批“多选消息 → 收藏”的准备操作。收藏入口仍适合用户已经筛选好的记录，尤其是聊天中夹杂大量无关内容时。

本轮查看的项目中，**尚未找到有充分证据证明可直接覆盖“Intel Mac + 微信 4.1.13 + 完整收藏聊天记录 + 文字及图片 + 批量准确记账”的成品**。部分项目可作为读取层参考；不能仅凭名字含“收藏导出”或“全部历史”就认定能直接使用。

建议顺序：

1. **近期：对指定私聊和当前收藏做一次并列可行性验证。** 优先读取系统提供的文字结构；图片使用本地 OCR。用相同记录比较操作量、漏采和核对成本，再选主要入口。
2. **随后：共享收件箱、玩家映射、检查点、异常核对和批量确认。** 两个入口共用账务逻辑，避免分别开发两套记账系统。
3. **大量历史资料或 Windows 环境：增加 JSON + 附件数据包导入。** 选定兼容的导出工具和格式后适配，可减少界面滚动；图片中的文字仍需识别。
4. **暂不作为 Intel Mac 默认安装方案：需要修改微信签名或系统保护设置的数据库提取工具。** 它们的部署条件与维护成本不符合第一版“轻松录入”的目标。

## 2. 各条路线的实际操作差异

| 路线 | 日常需要用户做什么 | 软件可自动做什么 | 适用情况与限制 |
| --- | --- | --- | --- |
| 文字／图片快捷录入 | 复制记录，选玩家或复用已确认来源 | 识别、解析、核对、批量确认 | 最容易落地，保留为通用入口；量大时复制次数仍多 |
| **直接读取指定私聊** | 首次绑定聊天与玩家；每批选聊天和范围、启动读取 | 定位聊天、读取文字、遍历范围、处理图片、恢复进度 | 有机会省掉收藏准备；需处理闲聊、本人回复、时间边界、撤回及修改；当前 Mac 版本未实测 |
| **读取收藏／收藏队列** | 在微信筛选并收藏；打开目标或选择一批 | 逐份打开、遍历、OCR、解析、集中核对 | 用户先筛选可减少无关内容；仍有收藏操作，且收藏可能丢失原始上下文 |
| **导入结构化聊天数据包** | 用兼容工具按联系人和时间导出，再把文件或目录导入松财 | 读取发送人、时间、顺序、文字及附件，增量检查、批量解析 | 大量历史资料更合适；需要适配真实导出格式和版本，并核验附件是否完整 |
| 直接读取本地微信数据库 | 完成依赖、版本和密钥等配置，后续运行采集 | 在本地已有数据范围内按条件读取，减少窗口操作 | 自动化潜力高，部署和版本维护较重；现有候选对 Intel Mac 有具体限制 |
| iPhone 备份导出 | 先有 iPhone / iPad，并制作可用备份，再导出 | 将备份中的聊天和媒体整理成文件 | 适合历史补录；用户是否使用 iPhone 未确认，不适合当作日常默认路径 |

“数据包导入”和“数据库提取”分开实现：松财可以只接收已经导出的资料，不必把修改微信环境、获取密钥等能力集成进客户端。导出器能读取的通常也是本机或备份中实际存在的数据，不能据此承诺所有历史和过期图片都能恢复。

## 4. 源码核对中影响选型的发现

### 4.1 FastBridge 有 Intel 读取层，但不是批量采集器

[构建配置](https://github.com/huj28-creator/wechat-fastbridge/blob/main/package.json)包含 `-arch arm64 -arch x86_64`，因此“支持 Intel”有构建层面的依据。它使用 macOS 辅助功能读取界面，作为松财原生辅助进程的参考较合适；仍需核对用户系统是否满足其 macOS 13+ 条件。

但在[原生实现](https://github.com/huj28-creator/wechat-fastbridge/blob/main/bridge/native/wechat_ax.m)中：

- 读取数量被限制在 1～20，默认 8；从当前收集的文字中取末尾部分。
- 输出主要是文字列表、聊天名和签名，不能当成含可靠原消息 ID、原图、时间及发送人字段的完整账务数据。
- 当前快照读取没有证明已经遍历目标时间段的全部历史。
- README 中的 favorite sticker 指“收藏表情”，不是“微信收藏中的聊天记录”。

因此，应参考系统读取和目标窗口核验；需要另做滚动检查点、原消息出现位置、图片提取、时间边界与缺口报告。其聊天名称模糊匹配、上下文压缩与摘要式返回不宜直接用于玩家身份确认和账目采集。

### 4.2 wxauto-mac 的“全部历史”只是当前消息表

[GetChatHistory 与内部实现](https://github.com/PatrickHua/wxauto-mac/blob/main/wxauto_mac/wxauto_mac.py)先导航聊天，再遍历 `message_table.children`。这条调用路径没有自动滚动加载历史的循环；寻找消息表时还使用了 `5 < 行数 < 200` 的判断。

可借鉴其控件查找方式，但短对话、超长对话和微信界面变化都要重新验证。不能把函数名或说明中的“all history”当作无遗漏保证。

### 4.3 “收藏批量导出”项目存在关键依赖缺口

[export_favorites.py](https://github.com/bugtest/wechat-favorites-export/blob/main/export_favorites.py)直接调用 `self.wcf.get_favorites()`，但本次读取的[WeChatFerry Python 客户端](https://github.com/lich0821/WeChatFerry/blob/master/clients/python/wcferry/client.py)中未找到这个方法。脚本未明确提供匹配的扩展实现，因此按当前公开代码不能认定可以直接运行成功。

该脚本只整理收藏的 id、type、title、content、时间、source、url 等字段并写文件，未见下载图片／附件或拆解合并聊天逐条消息的实现。这与 README 描述的“完整收藏数据和附件”存在差距。

### 4.4 收藏链接导出能参考操作流程，不能照搬完整性判断

[wechat-favlink-exporter](https://github.com/BigheadXL/wechat-favlink-exporter)作者报告其测试版本的收藏列表在 UIAutomation 树中不可见，所以采用坐标与剪贴板。**这是该作者针对 Windows 测试版本的结果，不能推广为所有微信版本或 Mac 都读不到。**

其[源码](https://github.com/BigheadXL/wechat-favlink-exporter/blob/main/wechat_fav_exporter.py)可参考校准、小批试运行和中断处理。链接按 URL 去重适合链接归档，但投注记录中两次相同正文可能是两笔真实记录，不能直接照搬；连续多次没有新内容也不能单独证明聊天已全部读完。

### 4.5 AI 自动回复的消息处理目标与算账不同

[wechat-mac-rpa](https://github.com/wq19901103wq/wechat-mac-rpa)的像素变化检测、OCR、SQLite 和消息对齐值得参考。但它的主流程会把截图交给配置的多模态 API，且对齐包含文字相似度等方式。

松财的第一版仍优先本地处理。金额、号码、发送人和原顺序必须保留证据；“避免机器人重复回复”的近似去重不能直接成为“删除重复投注”的规则。截图变化检测可以减少 OCR 工作，不能替代消息身份和完整性判断。

## 5. 推荐调整后的产品流程

### 5.1 入口一：读取指定私聊

目标流程：

> 首次绑定微信聊天与玩家 → 选择本次聊天和资料范围 → 自动读取文字、图片及顺序 → 异常集中核对 → 批量确认入账。

设计要点：

- 首次由用户确认聊天与账目玩家的映射。若只有显示名称，没有稳定标识，必须保留映射依据；同名不自动合并。
- 只读取本轮指定的聊天。若后续支持多聊天队列，应固定队列并串行操作微信窗口，避免相互抢焦点。
- 界面无法可靠确定日期边界时，让用户指定起点／终点，或把未确认部分标为待核对，不能只凭“今天”按钮承诺读完一天。
- 本人回复、系统消息和引用作为原始上下文保存，不自动新增投注。修改、取消按调整记录核对。
- 新任务可从上次检查点附近重叠读取，但必须核验连续性；上下文缺失时不能直接套用上次市场。
- 不要求玩家改变现有发送格式；使用现有解析规则，无法解析的内容集中处理。

该入口的价值是省掉准备收藏的操作，代价是软件需要更好地过滤无关消息并证明读取范围。若核对成本太高，收藏仍可能是更高效的主入口。

### 5.2 入口二：读取收藏和收藏队列

继续执行[微信收藏批量录入方案](微信收藏批量录入方案.md)。优先验证用户常用的聊天记录收藏，不把网页收藏或表情收藏的成功当成该功能成功。

收藏和直接私聊读取可能覆盖同一原始消息。能获得可核验的原消息标识时建立关联；只有正文和昵称一致时进入疑似重复核对，不能静默删除一份，也不能自动重复入账。

### 5.3 入口三：导入 JSON + 图片附件

先确定一个真实可用的导出器及版本，用导出样本实现适配，再逐步扩展其他格式。JSON 只是容器，不存在已经证实可通用读取的“微信标准导出 JSON”。

| 必须保存或检查的内容 | 目的 |
| --- | --- |
| 导出器及版本、来源账号／会话、原文件和导入批次 | 可追溯；避免不同来源的同名玩家混淆 |
| 原发送人、收发方向、原消息时间及原始顺序 | 区分玩家和本人回复，正确判断日期与上下文 |
| 消息类型、正文、引用关系、附件清单及本地文件 | 图片占位文字不能视为图片已导入；引用不能重复计费 |
| 原消息 ID（若有）及其作用范围 | 不同账号或会话中的 ID 不默认全局唯一；无 ID 时保留不确定性 |
| 导出范围、实际数量、缺失附件和异常项 | 区分“文件处理完”与“源聊天完整”；资料不足时报告缺口 |

首个版本可以让用户一次导入整个文件／目录；后续再评估本地待导入目录的自动发现。新文件先进入收件箱，经解析和核对后批量确认，不能把“文件到达”直接当作入账指令。

## 6. 与现有解析和账目规则的衔接

三个自动导入入口最终统一成“来源 → 原始消息 → 附件／OCR → 解析 → 核对 → 入账”，复用现有玩法解析器。界面适配层不负责猜测投注金额或修改业务规则。

- 默认市场为新；两边为新、旧，三边为新、旧、港。
- 同一原始记录段内，同一发送人连续内容继承市场，新的明确声明替换原市场。
- 发送人从 A 切到 B 再回 A 时，A 默认回到新，不恢复其早先的旧市场。
- 切换采集入口、重新打开聊天或导入第二份文件，本身不能证明记录连续。只有原始顺序和来源衔接明确时才复用上下文，否则显式提示。
- 业务日期决定农历生肖表；原消息时间、收藏时间、导出时间、采集时间分别保留。
- 两条真实的相同消息保留两次；同一次采集重试不得重复入账。

统一收件箱使用本地消息 ID 和入账关联，保留原始文件／图片及人工修正。现有以文档为单位、最多保存 200 份的结构不宜直接充当大规模微信消息队列；数据库和附件存储仍按原方案设计。

| 私聊与收藏对比 | 同一批已标注记录分别走直接私聊、收藏读取、快捷复制，统计准备、采集、校对总时间及点击次数 |
| 结构和图片 | 核对玩家、时间、收发方向、跨屏顺序；确认能取原图，或明确只能取截图及其局限 |
| 不漏采与不误删 | 加入两条相同真实消息、跨屏重叠、长图、本人引用、修改指令、加载失败；逐条对照原样本 |
| 持续批处理 | 小样本通过后再测试约 1000 条混合记录；验证中断恢复、微信升级后能力自检和窗口被切走时暂停 |
| 数据包路线 | 先拿到候选工具真实导出样本，核对格式版本、附件、消息 ID 范围及缺失字段；不凭产品截图认定可导入 |

决策原则：能完整读到私聊且人工核对量低，就以私聊入口为日常主路径；收藏更容易筛选或证明边界，就保留收藏为主；有兼容的结构化导出源且量大，则优先数据包。技术演示“读到了几条文字”不足以进入自动批量记账。

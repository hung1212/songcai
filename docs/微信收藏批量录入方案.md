# 微信收藏批量录入方案

版本：v0.2，补充 GitHub 调研与其他导入路线  
日期：2026-10-05  
适用项目：松财桌面客户端，Windows / macOS  
状态：完整设计目标；v0.2.0已交付部分功能，真实微信界面采集尚待实测。

**实施进展（2026-10-05）：** v0.2.0 已实现基础收件箱、截图＋OCR读取当前收藏、停止续读、核对入账与备份恢复。本文保留原完整目标，收藏列表队列、AX直接正文提取等尚未实现；真实微信收藏仍待授权后实测。以[第一版使用说明与验证边界](微信收件箱第一版使用说明.md)为当前交付范围。

## 1. 结论与目标

建议保留已认可的“文字／图片快捷录入”，同时将“从微信收藏批量读取记录”作为减少操作的重点方向，按两步实现：

1. **打开一份收藏，松财自动读取这份记录。** 用户在微信中打开目标收藏，启动一次读取；软件负责识别内容、翻页或滚动、处理图片、解析和汇总。
2. **指定一批收藏，松财按队列自动处理。** 在第一步验证可靠后，增加收藏列表识别，自动打开下一份、继续读取和断点恢复；合格记录统一确认，异常集中处理。

推荐的完整流程：

> 微信私聊中选取所需记录并收藏 → 打开目标收藏或指定收藏队列 → 自动读取文字和图片 → 识别玩家、业务日期和市场 → 解析与重复核对 → 一次确认合格记录入账 → 集中处理异常。

“收藏”用于集中待整理资料；“松财收件箱”负责保存采集结果、解析状态和入账状态。不能仅因为某份记录已经收藏，就认为它已经计入账目。

目标是减少逐条复制、切换软件、补写玩家和逐条确认。首版采用**自动采集、自动解析、批量确认入账**，不要求每条正常记录都点一次确认。

**2026-10-05 调研补充：** 已阅读 GitHub 上 11 个候选项目并抽查关键实现，详见[微信录入 GitHub 项目调研](微信录入GitHub项目调研.md)。建议在首轮验证中并列比较“直接读取指定私聊”和“读取当前收藏”：前者有机会省掉收藏准备，后者有利于先筛选有效资料。另预留“JSON + 图片附件数据包导入”用于大量历史资料或兼容的导出源。当前未找到足以证明可直接覆盖用户 Intel Mac、微信 4.1.13、完整收藏聊天及图片的现成方案，不能把项目名称或 README 中的功能描述视为实测结果。

## 2. 已确认条件与设计边界

### 2.1 用户已确认

| 条件 | 已知情况 |
| --- | --- |
| 接收方式 | 主要是一对一微信私聊 |
| 操作设备 | 电脑微信，目前用户使用 Intel Mac；软件同时面向 Windows |
| 当前微信版本 | 读取本机应用元信息得到 4.1.13（269602）；尚未验证该版本的界面采集能力 |
| 内容类型 | 文字和图片都有 |
| 工作量 | 记录量较多，优先减少重复手动操作；具体每天条数尚未确定 |
| 基础方案 | 认可玩家选择、文字／图片快捷录入、识别校对和批量确认 |
| 新需求 | 将记录收藏，在收藏中打开聊天记录后自动录入；评估批量读取收藏 |
| 软件目的 | 按玩家和新／旧／港市场整理投注账目，赔付功能后续引入 |

### 2.2 本文不把以下能力视为已经成立

- 未检查当前微信版本是否支持所需的多选收藏、标签筛选及独立查看窗口。
- 未验证收藏能否保留原发送人、原消息时间、聊天来源及完整消息顺序。
- 未验证 Mac 或 Windows 微信的辅助功能接口能否读到收藏正文。
- 未验证收藏列表、聊天记录窗口、图片查看器的自动滚动、加载和返回行为。
- 未验证能否获得可靠、稳定的收藏ID或原消息ID；不能用界面控件ID冒充原消息ID。
- 未测得采集速度、OCR准确率、每批可处理数量或最终人工节省比例。

因此，本方案是**有验证关卡的实施设计**，不是“微信收藏已经可以全自动读取”的承诺。先在用户的 Intel Mac 上验证，再决定 Windows 的具体适配方式。

### 2.3 方案设计阶段的范围

前期方案阶段只输出文档，没有控制微信、创建收藏或读取实际聊天。后续已按第一版范围实现代码，交付状态见本文开头。功能围绕已有记录的整理和本地记账；发送消息、自动回复、收付款和在线下注不属于本方案。

GitHub 调研只阅读了公开说明、部分源码和许可证，未安装或运行第三方项目；本机检查仅涉及微信应用版本元信息。

## 3. 收藏入口的几种形式

不同收藏形式携带的信息可能不同，不能共用一个未经验证的识别假设。

| 收藏形式 | 可能获得的信息 | 处理方式 |
| --- | --- | --- |
| 多条消息组成的聊天记录 | 可能有逐条发送人、时间、文字、图片及顺序 | 优先支持，先验证实际微信版本是否保留这些信息 |
| 单条文字收藏 | 可能只有文字及有限来源信息 | 来源不足时，整份绑定一次玩家和业务日期 |
| 单张图片收藏 | 图片及可能存在的来源描述 | OCR识别；图片中的昵称不能直接替代可靠的玩家绑定 |
| 合并转发后保存的聊天记录 | 外层转发者和内层原发送人可能不同 | 以内层原发送人为依据，不能把整份记到转发者名下 |
| 收藏笔记、手工整理内容 | 用户自行编辑的标题、正文和图片 | 作为独立资料导入，不能默认还原完整聊天身份和顺序 |

建议优先验证“同一个私聊内多条消息组成的一份收藏”。一次集中一位玩家的一个完整记录段，通常有利于减少玩家绑定次数，并保留市场声明与后续省略行的关系。

**不要为了减少收藏数量，把原来来自不同私聊的记录混成没有来源标记的一大段文字。** 丢失玩家和消息边界后，软件只能增加人工核对，无法可靠自动恢复。

### 3.1 “收藏微信记录”按钮如何设计

两种入口均纳入设计，但分开验收：

| 入口 | 具体行为 | 阶段 |
| --- | --- | --- |
| 用户通过微信收藏 | 用户在微信选择记录并收藏，松财从打开的收藏读取 | 首个可行性验证采用此入口，减少依赖 |
| 松财提供“收藏已选记录”快捷入口 | 用户已在微信明确选中记录；软件验证目标窗口与选中状态后，调用可用的“收藏”界面动作 | 后续可选；只有实际微信版本能可靠识别选区与结果时才实现 |

快捷入口不自动猜选“今天全部消息”，不把尚未加载的历史记录当作已经选中。若系统接口无法可靠读取选中范围，保留微信原生收藏操作，自动化精力优先投入读取和批处理。

## 4. 自动化程度对比与推荐顺序

| 级别 | 用户操作 | 软件自动处理 | 价值与限制 |
| --- | --- | --- | --- |
| A：快捷录入 | 复制文字／图片，触发快捷键 | 暂存、绑定建议、解析、疑似重复提示 | 已认可的基础入口，也是所有自动采集失败后的回退方式 |
| B：读取当前收藏 | 打开一份收藏，点击一次“读取当前收藏” | 定位正文、完整遍历、文字读取、图片识别、解析 | **先验证这一层**；用户不必逐条复制或手动滚动 |
| C：指定收藏队列 | 选定待导入范围并启动一次 | 打开各收藏、逐份读取、返回列表、继续下一份、断点恢复 | **大量记录的目标方案**；依赖B稳定及列表边界可识别 |
| D：打开后自动读取 | 显式开启本轮采集，再打开目标范围内的收藏 | 检测目标收藏窗口，自动创建或恢复读取任务 | 在B、C可靠后增加；无需每份再点读取按钮 |

“打开后自动读取”应有明确的采集开关和状态提示，只对本轮选定的微信窗口及收藏范围生效，不在用户未开启时持续读取其他聊天或收藏。

第一次设置玩家映射和采集范围后，后续尽量复用；需要重新核对的情况集中在来源不明、同名、日期不明、图片识别异常、重复疑点和内容修改。

## 5. 目标使用流程

### 5.1 每批只设置一次

启动本批导入时，确认：

- 记账业务日期；若混有历史资料，软件应按原消息日期提示拆分或核对。
- 读取范围：当前打开的收藏，或者明确选定的收藏队列。
- 玩家来源：已绑定的私聊来源、收藏中可验证的原发送人，或用户手动指定。
- 读取方式：优先直接读文字，图片和无法直接读取的区域走OCR。

候选队列可来自实际微信版本支持的标签、搜索结果、明确选择的列表范围，或用户逐份加入的收藏。建议约定一个“松财待整理”标签，**是否支持以及能否批量操作需实测**。标签只帮助选择范围，不作为入账成功凭据。

### 5.2 自动读取一份收藏

1. 验证当前窗口确实是目标收藏详情，记录标题、来源提示及读取起点。
2. 定位正文滚动区域，回到可验证的起点；只读当前屏幕不能算“整份完成”。
3. 按原顺序获取消息文字、发送人、时间和图片位置。
4. 对未完整加载的内容等待状态变化；对长记录继续滚动，保留相邻屏幕重叠区域作为连续性依据。
5. 遇到图片时优先取得实际图片内容；仅有缩略图或文字不可辨认时标记需要补充，不能当作已识别。
6. 验证到达结尾，并检查中间是否存在加载失败、跳页、裁切或未处理图片。
7. 保存来源证据和本地检查点，解析全部已读取内容；存在缺口时显示“部分读取”，不标记“完成”。
8. 返回队列处理下一份，用户只需要关注异常和最终汇总。

嵌套聊天卡片、超长图片及无法展开的内容各自记录为待处理子项。限制展开深度、重试次数和单项耗时，达到限制后保留位置并继续其他可处理项，不能静默跳过后宣布整批完成。

### 5.3 结束时集中处理

收件箱显示四组结果：

- **可入账**：来源、日期、玩家、内容及市场关系明确，解析没有未解决问题。
- **待核对**：OCR关键字段、疑似重复、合计冲突、修改／撤回引用、来源或上下文不明确。
- **采集未完成**：尚未读完、图片未加载或自动操作中断。
- **本批已处理**：已入账、明确跳过或确认属于重复采集的记录。

用户可以一次确认整批可入账项。图片在首个版本中仍需校对，但可以按玩家或收藏整组查看原图与识别结果，不必逐条弹窗确认。未解决项保留原文，不阻塞其他独立、完整记录的处理。

同一条多行消息只要还有关键金额、选号或上下文问题，就不应把其中部分结果伪装成“整条已确认”。

## 6. 玩家、日期和市场归属

### 6.1 玩家归属

归属依据优先使用经用户确认的来源映射；收藏内部原发送人与绑定结果冲突时必须提示，不能静默覆盖。

- 一份确定来自单人私聊的收藏，可一次绑定该玩家，覆盖其中全部适用记录。
- 姓名相同不等于同一人；昵称变化也不自动建立一个新的账目玩家。允许人工确认别名和来源映射。
- 如果无法获得稳定的来源标识，映射应显示其依据只是“标题／显示名称”，不能声称拥有微信账号级唯一身份。
- 合并转发以内部原发送人为准；外层收藏者、转发者与被记账玩家分别保存。
- 本人回复、系统提示、引用消息要单独分类。引用原文不能因为在回复里再次出现就自动计为新增记录。
- 图片中的玩家名与当前绑定不一致时进入待核对；不自动切换整份收藏的归属。

“绑定一次、整批复用”只在来源关系明确时成立，不能为了减少点击而把所有未署名内容都归到上一次处理的玩家。

### 6.2 日期

分别保存原消息时间、收藏时间、采集时间和记账业务日期。**收藏时间不能代替原消息时间。**

原消息日期明确时可以预填建议；缺少日期时按用户选择的本批业务日期处理，并保留该来源说明。跨日、历史收藏、只有“昨天”等相对时间但缺少可靠参照时提示核对。生肖展开仍严格使用账单业务日期对应的农历年。

### 6.3 市场继承：保持已确认规则，新增来源边界

同一原始记录段内部继续执行已有规则：

- 默认新；两边＝新＋旧；三边＝新＋旧＋港。
- 同一发送人连续内容继承完整市场集合；当前明确声明替换它。
- 切换为另一玩家的投注内容时重置默认新；A→B→A不恢复A之前的旧市场。
- 普通回复和系统提示作为非投注元信息，不能从其中猜测玩家投注市场；涉及顺序或引用关系不明时留待核对。

**收藏之间的衔接是本次新增问题，采用以下保守设计，尚需业务确认：**

| 情况 | 建议处理 |
| --- | --- |
| 一份完整、独立的收藏 | 独立解析上下文，默认新，显式声明优先 |
| 同一私聊被拆成两份收藏，且已确认原顺序连续、同一业务批次 | 可以明确关联为续篇，按来源顺序重建上下文 |
| 仅仅玩家名字相同，或收藏列表显示为相邻两条 | 不自动继承市场 |
| 收藏开头明显是“再加”“同上”等续写，或发现前文裁切 | 标记缺少前文，补采或核对，不能伪装成已经确定的新市场 |
| 多份收藏分批录入或倒序打开 | 不能以软件打开顺序推导原消息市场；独立处理或按已确认的来源顺序合并 |

例如第一份含“小明：旧 1 2 3 各100”，第二份只有“特肖虎100”，不能仅凭两个收藏都叫小明就自动继承旧。应将完整上下文一起收藏，或在导入时确认它们是连续记录。

界面应显示每笔市场及其来源：原文声明、继承自哪条消息、独立批次默认，或人工修正。修正前文后重算受影响的后续项，保留变更记录。

## 7. 重复与漏录：大量处理时的关键要求

### 7.1 区分重复采集与真实重复内容

| 情况 | 处理要求 |
| --- | --- |
| 同一读取任务滚动时，相邻屏幕重复露出同一消息 | 用可验证的重叠顺序和消息出现位置合并这次采集，不能重复生成账目 |
| 同一任务暂停后恢复，已持久化的本地消息再次处理 | 使用本地消息ID恢复，幂等处理，不再次入账 |
| 同一玩家确实连续发送两条相同文字 | 保留两次真实出现，不能按文字哈希直接去掉一条 |
| 不同收藏包含相同内容或同一张图片 | 仅提示疑似重复；除非有可靠的同源证据，不能自动扣除 |
| 转发、引用、收藏笔记中再次出现旧消息 | 保存外层和内层关系，关系不明时集中核对 |

文字哈希、图片哈希、玩家名加分钟级时间、截图坐标，都不能单独证明是同一条真实消息。微信界面控件的运行时ID可能被回收，也不能作为全局消息ID。

本地生成的ID能保证“这次已经导入的记录不被再次提交”，但不能凭空解决“两次不同收藏是否包含同一条微信消息”的判断。跨收藏只有弱证据时，允许用户整组确认重复或保留两次，并保存该决定。

对滚动重叠的匹配，重复句式过多、锚点不唯一、列表变化等情况必须降低确定性，不能任意合并并宣称没有漏录。

### 7.2 完整性

- 每份收藏记录起点、终点、滚动检查点和未处理子项。
- 有明确界面边界或完整遍历证据，才可标记“读取完成”。连续两次画面不变可能是卡顿或加载失败，不能单独作为到达末尾的证据。
- 顶部不完整、底部未读完、图片缺失、折叠卡片未展开分别显示数量或位置。
- 有可信的原文合计、消息数量时进行交叉校验；不得假设微信一定提供总消息数，也不能靠金额相等证明全部采集正确。
- 收藏是用户选取的资料，软件只能说明“这份收藏是否读完”，不能声称“玩家今天全部微信消息均已录入”。

### 7.3 修改、撤回与版本变化

“上条取消”“改成200”“这张作废”等进入修改待核对流程，保留原记录和调整记录的关联。收藏内容未必随原聊天后续变动同步更新，不能假设撤回或修改会自动传播到软件。

重新读取内容发生变化的收藏时，显示新增、变化和可能缺失的部分；不得直接删除已入账的旧结果。完成确认后按明确的调整过程处理。

## 8. 自动读取的技术路线

### 8.1 读取优先级

1. **系统辅助功能接口读取可见文字及结构。** 能取得文字就尽量避免对清晰文字再做OCR。
2. **针对目标消息的界面复制动作。** 只有能明确定位消息、验证复制结果且不会错用旧剪贴板时，才作为适配方式。
3. **目标窗口／内容区域截图与本地OCR。** 用于图片、截图及接口无法读到的绘制区域。

这三种方式是候选组合，具体顺序可因微信版本调整；不预设微信一定向辅助功能接口暴露完整正文。

所有文字保留原始版本和标准化副本；OCR字形不确定时不自动把`10`改成`01`、把`1000`改成`100`。金额恰好能通过语法校验，也不能证明OCR正确。

### 8.2 平台适配

| 项目 | macOS候选路线 | Windows候选路线 | 验证重点 |
| --- | --- | --- | --- |
| 窗口与控件定位 | Accessibility / AX接口 | UI Automation | 收藏正文、来源标题和滚动区域是否可读 |
| 页面操作 | 可验证的控件动作，必要时目标窗口内坐标动作 | 控件模式、滚动与调用动作，必要时目标窗口内坐标动作 | 动作后是否仍在预期页面，避免固定坐标盲点 |
| 截图 | 系统提供的窗口／区域捕获能力 | 系统提供的窗口捕获能力 | 最小化、遮挡、显示缩放及多屏影响 |
| OCR | 优先评估系统Vision及中文识别效果 | 评估系统OCR／中文语言资源或本地OCR引擎 | 小字号、长图、压缩图、不同字体和关键数字 |
| Electron集成 | 原生辅助进程或模块 | 原生辅助进程或模块 | 打包、签名、权限、进程生命周期及错误回传 |

Mac需要按实际实现申请辅助功能和屏幕录制等系统授权；Windows的窗口权限级别、系统版本及OCR语言资源也要实测。权限缺失时清楚提示并提供手动录入回退，不能不断重试空白截图。

操作依据应组合窗口身份、控件角色、可见标题和页面状态，而不是只记住某个像素坐标。微信更新后执行能力自检，不能沿用失效的点击位置继续批量操作。

### 8.3 自动滚动与窗口占用

- 同一时间只安排一个微信界面采集任务，避免多个任务抢焦点、相互滚动。
- 滚动前后验证窗口、收藏身份和内容变化；捕获稳定画面后再读取。
- 用户切换到另一个聊天、关闭详情、锁屏或改变窗口状态时暂停；确认回到预期来源后才能继续。
- 需要窗口可见或前台时，在界面明确提示。未验证之前，不承诺最小化、遮挡或后台状态下也能完整采集。
- 长图片若只能局部显示，需要分段采集与覆盖校验；不能把预览缩略图当成原图完成识别。
- 图片OCR和文本解析可在采集后并行处理，但应限制并发，避免大量图片使Intel Mac卡顿。

首个版本以本地处理为目标。云端OCR仅作为效果不足时另行评估的方案，未选用前不上传聊天或图片。

### 8.4 GitHub 调研带来的实现选择

- **Mac 原生读取参考：** FastBridge 有 Intel 构建和 AX 读取代码，但现有快照最多返回 20 项近期文字；wxauto-mac 的历史读取仅遍历当前消息表。两者都不能直接证明收藏、全部历史或原图可完整采集。
- **收藏界面读取参考：** wechat-favlink-exporter 在作者测试的 Windows 4.1.8.67 上使用坐标和剪贴板，其任务仅为导出网页链接。该版本收藏列表不暴露 UIAutomation 的反馈值得验证，但不能外推到 Mac 或其他微信版本。
- **私聊入口：** 复用来源绑定、滚动检查点和收件箱，单独验证直接读取指定私聊及其图片。来源、时间边界和完整性仍必须明确；省去收藏准备不意味着能省去账目核对。
- **数据包入口：** 对选定导出器的 JSON 与附件增加适配层，可减少界面滚动。先检查真实样本中的发送人、消息顺序、时间、ID 作用范围及缺失附件，不假定所有 JSON 都兼容。现有候选有 Windows／Apple Silicon 限制，尚未确认用户 Intel Mac 可直接使用的完整图文导出器。

具体项目、源码证据、许可证与取舍见[GitHub 调研文档](微信录入GitHub项目调研.md)。这些是后续设计候选，尚未加入客户端；无论来源入口是什么，都不能用正文相似度自动删除真实的重复投注。

## 9. 软件界面与状态

### 9.1 微信录入入口

保留三种并列入口：

- 粘贴文字／图片。
- 读取当前收藏。
- 管理收藏读取队列。

根据 GitHub 调研，另纳入“读取指定私聊”和“导入聊天数据包”候选入口，分别通过兼容性与样本验收后再加入界面；它们复用同一收件箱和确认流程。

一眼可见本批业务日期、当前来源、当前绑定玩家、是否正在自动读取，以及已完成和待处理数量。

### 9.2 收藏队列

每项显示收藏标题、来源证据、玩家绑定、读取状态、已发现消息数、图片数和异常原因。没有可靠总量时显示“已发现”而不是编造“共多少条”。

队列启动时固定本轮范围；运行期间新增的收藏作为新发现项另行提示，不悄悄扩展本批范围。若列表倒序、置顶、更新收藏导致排序变化，应依赖已保存的来源证据重新核对，不能仅凭“上次读到第5行”续跑。

### 9.3 状态分别保存

```text
采集：排队 → 读取中 → 已完整读取
                  ↘ 暂停／部分读取／采集失败

记账：待解析 → 可入账 → 已入账
             ↘ 待核对 → 修正后重新解析
             ↘ 明确跳过／已确认重复
```

采集完成不等于已经入账，读取失败也不能删除已保存的原始内容。

### 9.4 核对与批量操作

- 左侧原文／原图，右侧识别文字、玩家、市场来源及金额。
- 按收藏、玩家或异常类型批量处理，减少逐条切换。
- 提供“绑定这一来源”“确认这一组为重复”“确认合格项入账”等批量动作；有冲突的项不混入无提示的批量操作。
- 明细可定位到收藏、消息和截图区域；从软件跳回微信原位置仅在来源定位能力已验证时提供。
- 当前应用关闭时保存检查点并退出，沿用v0.1.1的生命周期修复，不为快捷采集偷偷恢复长期后台驻留。

后续可评估对稳定来源、纯文本、无异常记录自动记账的可选模式。首版不默认启用；OCR置信分数不能单独成为自动记账依据。

## 10. 与现有客户端的衔接

### 10.1 可复用部分

- 现有玩法解析器、生肖农历切年、固定五行及分类规则。
- 整数分金额、组合计数、玩家分市场汇总。
- 明细追溯、问题提示和本地保存思路。

### 10.2 需要新增的部分

现有软件以文本文件为主要来源，保存结构最多支持200份文档，不适合把每条微信消息都新建成一个文件。大量录入应新增消息收件箱和持久化队列，不能只扩大文件列表或反复解析全部历史原文。

建议使用本地数据库保存结构化记录，图片独立保存在附件目录；现有JSON账单继续支持导入和备份，迁移前保留旧文件，不能无提示覆盖原草稿。

| 数据 | 主要字段及用途 |
| --- | --- |
| 导入批次 | 本地批次ID、业务日期、选定来源范围、创建时间、运行状态 |
| 收藏来源 | 本地来源ID、可验证的微信来源标识（如有）、原始标题、绑定证据、读取版本、完整性状态 |
| 来源消息 | 本地消息ID、原发送人、玩家ID、本人／对方／系统／引用分类、原消息时间及可信程度、原顺序、文字或图片引用 |
| 采集证据 | 截图区域、原图引用、读取方式、界面版本、前后锚点、缺口和重试情况 |
| OCR结果 | 原始识别文字、人工修正文字、关键字段疑点、使用的引擎版本 |
| 解析结果 | 规则版本、玩法、选项、份数、计费单位、整数分金额、市场及来源、问题列表 |
| 记账关联 | 来源消息ID、解析版本、入账状态、调整关系、每市场明细ID |
| 运行检查点 | 当前收藏、已保存的消息出现位置、读取边界和未处理子项 |

以上ID均为设计中的本地字段，不表示已经能从微信界面取得全局消息ID。

解析入口应支持结构化的发送人和消息顺序，不依靠把昵称随意拼接成“姓名：正文”后重新猜身份。可新增消息适配层，复用现有玩法解析逻辑，并补充跨消息续写与原文定位测试。

确认入账时使用本地消息及解析版本的唯一关联，在事务中提交；重复点击、任务重试或程序恢复都不能再次累计同一份已确认结果。来源关系不明的跨收藏重复仍按第7节处理。

只重算本次新增内容和上下文修改影响的记录段。列表分页显示，原图按需加载，OCR设置缓存与并发上限；不得因重新运行解析而把整批金额追加一遍。

## 11. 可行性验证计划

### 11.1 先验证用户的Intel Mac

| 步骤 | 要验证的内容 | 输出 |
| --- | --- | --- |
| P01 | 当前微信版本、系统版本、收藏入口和不同收藏实际形态 | 支持范围与界面样本 |
| P02 | 收藏中的原发送人、时间、正文、图片和原顺序是否保留 | 来源字段可用性清单 |
| P03 | 辅助功能树是否能读正文及定位滚动区域 | 直接读取可用／部分可用／不可用的结论 |
| P04 | 一份跨多屏收藏的起点、结尾、加载、滚动重叠与重复消息 | 已知样本逐条对照结果，明确完整性判断方法 |
| P05 | 图片获取、缩略图展开、长图和OCR关键数字 | 图片读取路径、人工核对量和失败分类 |
| P06 | 收藏列表筛选、打开、返回、排序变化和断点恢复 | 是否可以进入队列自动读取阶段 |
| P07 | 同源重读、跨收藏重叠、两条真实相同消息 | 重复提示与不重复入账验证 |
| P08 | 对同一批记录直接读取指定私聊，与收藏、快捷复制比较 | 准备、采集、核对总耗时及操作次数，决定主要入口 |
| P09 | 候选导出器真实 JSON 与附件样本 | 确认可用平台、格式版本、逐条来源字段与缺失附件，决定是否适配 |

完成Mac结论后，在Windows上独立重复相关步骤。不能把一端的成功当作另一端已经支持。

### 11.2 方案取舍关卡

- 若能直接读到完整文字及结构，优先做B，再做C。
- 若正文只能截图，但边界可稳定识别且人工核对工作量可接受，采用混合读取，明确哪些内容需要校对。
- 若当前收藏能读但收藏列表遍历不可靠，先交付B，用户打开下一份后自动接续；不宣称已支持全部收藏队列。
- 若既不能稳定确认来源，也不能证明整份内容已读完，不启用无人值守批量入账；保留快捷粘贴及图片核对入口。
- 若创建收藏的手动成本高于直接批量复制，保留两种入口，让实测操作量决定主要路径，不强制所有资料都经过收藏。
- 若指定私聊能可靠保留来源、顺序和读取边界，且总操作量更低，将其作为日常主入口；收藏继续用于已筛选资料，两者共用收件箱。
- 若有可用的结构化导出源，大批历史资料优先评估数据包导入；不能因项目声明支持 Mac 就假定其 ARM64 安装包可在 Intel 上运行。

## 12. 验收用例与指标

### 12.1 正确性用例

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| W01 | 单人收藏含“旧1 2 3各100；特肖虎100” | 旧市场400元，继承来源可见 |
| W02 | 同一原始记录中A→B→A，返回A时无市场声明 | 按已确认规则重置新，不恢复A旧市场 |
| W03 | 两边声明后连续多条省略市场 | 新、旧分别入账，集合完整继承 |
| W04 | 同一玩家两条完全相同的真实消息 | 保留两次出现，不按正文哈希自动删一条 |
| W05 | 滚动重叠造成同一消息被读取两遍 | 能证明同一次出现时仅保留一次；不能证明时提示 |
| W06 | 两份收藏部分重叠但没有可靠原消息ID | 提示疑似重复，不擅自合并或丢弃 |
| W07 | 同一任务重复启动、暂停恢复、重复点击确认 | 已关联的本地消息不重复累计金额 |
| W08 | 图片“各100”被识别成“各1000” | 不能因金额语法合法就直接自动入账，原图可核对 |
| W09 | 图片缺失、收藏只读到中段、卡片未展开 | 保留缺口和位置，不能显示整份完成 |
| W10 | 私聊来源绑定小明，但内部出现另一原发送人 | 提示归属冲突，不把全部消息记给小明 |
| W11 | 本人回复引用玩家原文 | 引用不自动作为新的玩家记录累计 |
| W12 | 原消息是昨日，今日才收藏 | 收藏时间不覆盖原消息时间；业务日期显式核对 |
| W13 | 农历切年前后的历史消息混在收藏中 | 分别按确定的业务日期展开，不能统一用采集当天生肖 |
| W14 | 出现“上条取消／改成200” | 建立待核对调整，不静默新增或覆盖旧账 |
| W15 | 微信切换窗口、锁屏、权限撤销或退出 | 暂停并保存进度，不操作其他窗口、不报假完成 |
| W16 | 收藏内容编辑、列表顺序改变或新增收藏 | 重新核对来源，不能按列表下标盲目续跑 |
| W17 | 标题同名但实际不同玩家 | 不自动合并账目，支持分别绑定 |
| W18 | 采集或OCR完成时崩溃，随后重新打开松财 | 从已保存检查点恢复；已确认数据仍在、未确认项不丢失 |

### 12.2 建议测试规模

先用少量已人工标注的收藏验证路径，再扩大到多玩家、多份跨屏记录的混合批次。建议包含至少一批1000条量级的文字／图片混合测试，其中故意加入真实重复、跨收藏重叠、长图、加载失败和历史日期。该规模是验收建议，不代表已经测得用户日量。

分别记录：

- 已知样本的消息覆盖率、漏采数、错归玩家数和关键金额错误数。
- 真正重复采集是否被阻止，真实重复消息是否被错误丢弃。
- 每100条记录需要的人工操作次数，以及每100张图需要的校对次数。
- 收藏准备时间、采集时间、OCR时间、核对时间分别统计，不只展示解析器耗时。
- 队列断点恢复后新增的重复入账数和丢失数。
- Mac、Windows各自的微信版本、硬件、缩放比例、内存占用和耗时。

已标注验收集中的错误玩家归属、漏记却报告完成、重复入账、未经核对的错误金额必须修正后再放行。有限测试集通过不等于承诺所有未知图片和微信版本都100%正确。

操作效率目标以快捷录入方案为基线：争取显著减少逐条操作；只有在总操作时间和异常处理量确实下降时，才扩大自动化范围。暂不承诺“几秒处理几千条”等未经测量的速度。

## 13. 建议实施顺序

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 第一步：私聊与收藏读取验证 | Intel Mac、微信 4.1.13 上的私聊与收藏正文、来源、跨屏完整性及图片路径对比报告 | 明确可用能力和失败边界，比较总操作量，决定主要入口 |
| 第二步：基础收件箱 | 文字／图片快捷录入、玩家绑定、消息存储、解析、核对、批量确认 | 手动入口可独立完成记账；新旧账单兼容 |
| 第三步：自动读一份收藏 | 读取当前收藏、自动滚动、图片OCR、完整性提示、暂停恢复 | 通过单收藏及重叠／重复／中断测试 |
| 第四步：收藏队列 | 指定范围、逐份读取、失败项保留、运行检查点与批量确认 | 批量测试证明减少人工操作且不漏录、不错归、不重复入账 |
| 第五步：Windows适配及快捷增强 | Windows采集适配；可行时增加打开自动读取、收藏已选记录等入口 | 各功能在对应版本独立验收 |

第一步是小规模验证，不要求先开发完整自动化系统。基础收件箱与截图OCR采集第一版现已实现；真实微信兼容性、完整性和效率仍按上述关卡验收。

若首轮对比选择私聊为主要入口，第三、四步优先实现对应的单聊天读取与指定聊天队列，收藏路径仍按独立验收结果推进。数据包导入在拿到兼容导出样本后另行适配，不作为界面采集必须等待的前置条件。

## 14. 实施前需要核对的少量信息

以下问题用于实测和业务收敛，不影响本文先行交付，也不自动视为用户已经同意某种默认行为。

1. 实际收藏是哪种形式：多条聊天记录、单独文字／图片，还是整理后的笔记；能看到哪些原发送人和时间信息？
2. 当前Mac微信版本已核对为4.1.13；仍需验证系统版本、收藏窗口形式及所需的Windows兼容范围。
3. 同一私聊拆成多份收藏时，是否允许明确关联为续篇；默认独立解析是否符合日常操作？
4. 本批资料是否经常跨日、是否包含用户本人回复和修改／取消指令？
5. 正常批次采用“一键批量确认”是否足够；实际文字／图片比例和每日大致条数是多少？

优先通过少量真实界面样本回答技术问题，不要求用户先逐条整理大量资料。后续验证应先检查用户常用的收藏方式，避免设计成一个需要改变全部微信操作习惯才能工作的功能。
